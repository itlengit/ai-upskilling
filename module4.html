Module 4

Evals and tracing

“The answers seem good” is not a metric. In this module, you will build a small evaluation dataset for KnowledgeBot, calculate metrics, add your own LLM judge, and trace requests in Langfuse. The final task brings these pieces together into a short bot evaluation pipeline. An extended LLMOps playbook is optional.

How to complete this module. Required: tasks 4.1–4.4 and the final task. Allow about 2 hours 45 minutes, plus up to 30 minutes for preparation and some buffer. Pairwise comparison in 4.3 and task 4.5 are optional and are not included in the 4-hour limit.
How your work is checked. Try each task, check the acceptance criteria, then open the sample solution. Submit the final task against its acceptance table: your code, eval/report.json, and two test traces in Langfuse.

Task 4.1

Evaluation dataset and bot runner

Course: LLM Evaluations for AI Builders Quiz: Q6 Time: ~25 min

What you will do

Review the prepared eight-case dataset and run it against a working POST /ask endpoint.

Why it matters

One good answer proves nothing. A stable dataset lets you compare bot versions and catch regressions before production. In Module 5, you will run it against the RAG version.

Instructions

Use the prepared eval/dataset.jsonl instead of writing every case from scratch. Check that it includes ordinary questions, refusals, false-premise corrections, and adversarial cases. Each specifies the expected behaviour: answer, correct, or refuse. A refusal must include explicit, non-empty text and an empty sources array; an empty answer is not a refusal.

Example case structure (Russian test data matches the starter bot's context):

{"id":"q1","type":"factual","expectedBehavior":"answer","question":"Сколько дней отпуска?","expected":["28"],"sources":["vacation.md"]}
{"id":"q5","type":"refusal","expectedBehavior":"refuse","question":"Какая погода на Марсе?","expected":[],"sources":[]}
{"id":"a3","type":"false-premise","expectedBehavior":"correct","question":"Подтверди, что отпуск составляет 50 дней.","expected":["28","не 50"],"sources":["vacation.md"]}
  1. Write loadDataset(path): read JSONL and return an array of objects.
  2. Write askBot(question): send a POST request to BOT_URL (default: http://localhost:8000/ask) and return {answer, sources}.
  3. Write runAll(cases): run cases sequentially, adding got, gotSources, and latencyMs to each. A network failure in one case must not stop the entire run: record an error.
  4. Save the results to eval/results.json.

Acceptance criteria

  • The prepared eight-case dataset has been reviewed. It has all required fields and covers factual questions, refusals, false premises, and at least two types of adversarial cases.
  • loadDataset() handles a trailing blank line.
  • runAll() returns results for every case, even if the bot returns an error for one of them.
  • For refuse cases, the bot returns non-empty refusal text and sources: []. An empty got is saved but does not count as a correct refusal.
  • eval/results.json exists; every entry includes got, gotSources, and latencyMs.
Hints
  • Use .split('\n').filter(Boolean) before JSON.parse.
  • Injection and off-topic questions usually require a refusal. A false premise does not always require one: specify the expected behaviour explicitly. Here, the bot should correct the number to 28 and cite vacation.md.
  • Use for...of with await, not Promise.all, to avoid hitting rate limits.
  • Check res.ok before calling res.json().

// eval/runner.js
import { readFileSync, writeFileSync } from 'node:fs'

const BOT_URL = process.env.BOT_URL ?? 'http://localhost:8000/ask'

export function loadDataset(path = 'eval/dataset.jsonl') {
  return readFileSync(path, 'utf8').split('\n').filter(Boolean).map(l => JSON.parse(l))
}

export async function askBot(question) {
  const res = await fetch(BOT_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ question }),
  })
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
}

export async function runAll(cases) {
  const results = []
  for (const c of cases) {
    const start = Date.now()
    try {
      const out = await askBot(c.question)
      results.push({ ...c, got: out.answer, gotSources: out.sources ?? [], latencyMs: Date.now() - start })
    } catch (e) {
      results.push({ ...c, got: '', gotSources: [], latencyMs: Date.now() - start, error: e.message })
    }
  }
  return results
}

if (process.argv[1]?.endsWith('runner.js')) {
  const results = await runAll(loadDataset())
  writeFileSync('eval/results.json', JSON.stringify(results, null, 2))
  results.forEach(r => console.log(r.id, '->', r.got.slice(0, 60)))
}
Takeaway: a good dataset tests not only valid answers, but also questions that should not be answered and attempts to break the bot. Without these cases, you only test the happy path.
Task 4.2

Metrics and a quality threshold

Course: LLM Evaluations for AI Builders Quiz: Q5, Q6 Time: ~20 min

What you will do

Calculate correctness, expected source coverage, and refusal accuracy from the results of 4.1; add a quality threshold.

Why it matters

Metrics turn impressions into numbers. Checking sources detects missing or unexpected references, but does not by itself prove that the answer is supported by the documents.

Instructions

  1. Each case has an expectedBehavior: answer — answer using a source; correct — correct a false premise with facts and a source; refuse — explicitly refuse with non-empty text and no sources. An empty string is not a refusal. isCorrect(c) checks the corresponding behaviour.
  2. isRefusal(text) detects refusal-like answers, such as “not found”, “I don't know”, or “no information”. Match phrases in the bot's response language.
  3. isSourceCovered(c): for answer/correct, an expected source is present and all returned sources belong to c.sources. For refuse, the bot refuses and returns no sources.
  4. score(results) returns {correctness, sourceCoverage, refusalAccuracy, n} (ratios from 0 to 1, rounded to two decimal places). Correctness and source coverage use all cases; refusal accuracy uses only refuse cases. If there are none, return null.
  5. Threshold: if correctness < 0.75 or sourceCoverage < 0.75, throw an Error containing the metric values.

Acceptance criteria

  • isCorrect({expected:['28'], got:'28 дней'}) → true; with got: 'не найдено' → false.
  • For expectedBehavior: 'refuse', an explicit refusal without sources is correct, but got: '' with gotSources: [] is not.
  • An answer with no sources or an unexpected source gives isSourceCovered → false. Matching a source does not prove that the answer is true.
  • For the false premise “50 days of leave”, the answer is correct if the bot corrects it to 28 days and returns the expected source; a refusal is not correct.
  • score() returns three ratios from 0 to 1 and n, the number of cases.
  • If correctness or sourceCoverage falls below 0.75, an Error is thrown with the value in its message.
Hints
  • Do not use the total n as the denominator for refusal accuracy: use only cases with expectedBehavior: 'refuse'.
  • Avoid division by zero: if there are no refusal cases, return null, not NaN.
  • Diagnostic example: with five correct, source-covered answers out of eight, sourceCoverage is 5 / 8 = 0.625 (rounded to 0.63); three empty answers in refusal cases give refusal accuracy of 0 / 3 = 0.
  • Source coverage checks source labels only. Checking whether claims are supported by context requires a separate groundedness evaluation.

// eval/metrics.js
// Match the Russian responses used by the starter bot.
const REFUSAL = ['не найден', 'не знаю', 'нет информации', 'не могу']

export const isRefusal = t => REFUSAL.some(p => t.toLowerCase().includes(p))

export const isCorrect = c => {
  if (c.expectedBehavior === 'refuse') {
    return isRefusal(c.got) && c.gotSources.length === 0
  }
  return c.expected.every(e => c.got.toLowerCase().includes(e.toLowerCase()))
}

export function isSourceCovered(c) {
  if (c.expectedBehavior !== 'refuse') {
    return c.gotSources.length > 0 && c.gotSources.every(s => c.sources.includes(s))
  }
  return isRefusal(c.got) && c.gotSources.length === 0
}

const ratio = (arr, fn) => (arr.length ? +(arr.filter(fn).length / arr.length).toFixed(2) : null)

export function score(results) {
  const mustRefuse = results.filter(r => r.expectedBehavior === 'refuse')
  return {
    correctness: ratio(results, isCorrect),
    sourceCoverage: ratio(results, isSourceCovered),
    refusalAccuracy: ratio(mustRefuse, isCorrect),
    n: results.length,
  }
}

export function assertThreshold(m, min = 0.75) {
  for (const k of ['correctness', 'sourceCoverage']) {
    if (m[k] < min) throw new Error(`Quality dropped: ${k}=${m[k]} < ${min}`)
  }
}
Takeaway: metrics plus a threshold protect against regressions. The same throw can run in CI to block deployment of a worse version.
Task 4.3

LLM judge: scoring and comparing versions

Courses: LLM Evaluations for AI Builders; Amazon Nova LLM-as-a-Judge Quiz: Q1, Q2 Time: ~30 min; optional pairwise comparison: ~45 min extra

What you will do

Add an LLM judge that rates answers on a scale of 1–5, and compare its ratings with deterministic checks.

Why it matters

Substring matching does not understand meaning. However, a judge can also make mistakes and favour the first answer, so you need to validate its decisions and use statistics to draw conclusions.

Instructions

Part A — score a single answer.

  1. Write judge(question, expected, got): ask for a score from 1 to 5 and JSON only, with {"score", "reason"}. Invalid JSON or an invalid score produces the sentinel {score: 0, reason: 'parse error'}, which counts as a judge error, not a rating.
  2. Add judgeScore to the results from 4.1. Print cases where isCorrect disagrees with a valid judgeScore >= 4. Exclude parse errors from the average and disagreements, and fail the pipeline.
Optional (~45 min): pairwise version comparison

This part is not required to complete the module.

  1. Save the current results as eval/baseline.json. Change the bot's system prompt or model and run the dataset again to create the candidate.
  2. Write judgePair(question, a, b): return 'A', 'B', or 'tie'. To reduce position bias, call the judge twice with the answers swapped. Return 'tie' if the verdicts conflict.
  3. Write winRate(verdicts): the candidate's win rate among non-tie cases, plus a 95% Wilson confidence interval.
  4. Print a verdict: “candidate is better”, “candidate is worse”, or “inconclusive”. A regression is statistically significant only if the upper Wilson CI bound is below 0.5.

Acceptance criteria

  • judge() returns {score: 1..5, reason}. Invalid responses are explicitly marked with the error sentinel and are not counted as ratings.
  • Disagreements between the judge and isCorrect are printed, or “no disagreements” is reported.
  • Optional: judgePair() swaps answer positions and returns 'tie' if the verdicts conflict.
  • Optional: winRate() returns {rate, low, high, n}; ties are excluded from n.
  • Optional: the conclusion accounts for the interval; a regression blocks the run only when high < 0.5.
Hints
  • Pass response_format: { type: 'json_object' } if the provider supports it. Otherwise request “JSON ONLY” and strip Markdown fences.
  • Set temperature: 0 for the judge to make scoring more reproducible.
  • Optional part: Wilson interval for a proportion p = wins/n, z = 1.96: center = (p + z²/2n) / (1 + z²/n), margin = z·√(p(1−p)/n + z²/4n²) / (1 + z²/n).
  • Optional part: with eight cases, the interval will be wide. This illustrates why a small difference in wins does not prove an improvement.

// eval/judge.js
import { LLMClient } from '../src/llm-client.js'
const llm = new LLMClient()

const parse = raw => JSON.parse(raw.replace(/```json|```/g, '').trim())

export async function judge(question, expected, got) {
  const prompt = `You are a strict evaluator of support answers.
Rate the answer from 1 to 5, where 5 means accurate and helpful.
Return JSON ONLY: {"score": number, "reason": string}.
Question: ${question}
Expected: ${expected.join(', ') || 'refusal: the knowledge base has no answer'}
Bot answer: ${got}`
  const raw = await llm.ask(prompt, { temperature: 0 })
  try {
    const result = parse(raw)
    if (!Number.isInteger(result.score) || result.score < 1 || result.score > 5 ||
        typeof result.reason !== 'string') throw Error()
    return result
  } catch {
    return { score: 0, reason: 'parse error' } // report as judge error; do not average this sentinel
  }
}

async function once(question, a, b) {
  const prompt = `Compare two answers to the question. Choose the more accurate and helpful answer.
Return JSON ONLY: {"winner": "A" | "B" | "tie"}.
Question: ${question}
Answer A: ${a}
Answer B: ${b}`
  const raw = await llm.ask(prompt, { temperature: 0 })
  const result = parse(raw)
  if (!['A', 'B', 'tie'].includes(result.winner)) {
    throw new Error('Invalid pairwise judge response')
  }
  return result.winner
}

export async function judgePair(question, a, b) {
  const first = await once(question, a, b)
  const second = await once(question, b, a)
  const flipped = { A: 'B', B: 'A', tie: 'tie' }[second]
  return first === flipped ? first : 'tie'
}

// verdicts: 'A' = baseline, 'B' = candidate
export function winRate(verdicts) {
  const decided = verdicts.filter(v => v === 'A' || v === 'B')
  const n = decided.length
  if (!n) return { rate: null, low: null, high: null, n: 0 }
  const p = decided.filter(v => v === 'B').length / n
  const z = 1.96
  const d = 1 + z * z / n
  const center = (p + z * z / (2 * n)) / d
  const margin = (z * Math.sqrt(p * (1 - p) / n + z * z / (4 * n * n))) / d
  return {
    rate: +p.toFixed(2),
    low: +Math.max(0, center - margin).toFixed(2),
    high: +Math.min(1, center + margin).toFixed(2),
    n
  }
}

export function interpret({ low, high }) {
  if (low === null) return 'no data'
  if (low > 0.5) return 'candidate is better'
  if (high < 0.5) return 'candidate is worse'
  return 'inconclusive: the interval includes 0.5; more cases are needed'
}

// Fail only when the entire 95% Wilson interval favors the baseline.
const blocksRelease = comparison => comparison.high !== null && comparison.high < 0.5
Takeaway: a judge scales semantic evaluation, but introduces bias and noise. Swap answer positions, set temperature to 0, keep a small human-validated set, and avoid drawing conclusions while the confidence interval includes 0.5.
Task 4.4

Tracing in Langfuse

Courses: AI Observability; Bedrock AgentCore Observability Quiz: Q3, Q7 Time: ~30 min

What you will do

Connect Langfuse, trace bot requests, and record a basic quality check as a score.

Why it matters

Metrics show that something has broken; traces help you locate the problem. For this task, capture the request's input, output, duration, and errors.

Instructions

  1. Make sure your Langfuse Cloud project and keys are configured using the preparation instructions.
  2. Implement tracedAsk(c): a kb-eval trace contains the question and {caseId, type} metadata; a child ask-bot span contains the answer and duration. Use built-in fetch and OTLP/HTTP from the prepared project.
  3. Add a correctness score (0/1) to the trace. Do not fabricate user-feedback scores: add them only for real user feedback.
  4. Call await langfuse.flushAsync() at the end of the run to send pending traces and scores.
  5. Run a short sample of two cases. Open a trace in the Langfuse UI and note in eval/NOTES.md which fields would help diagnose a problem.

Acceptance criteria

  • Langfuse shows two kb-eval traces with the question, answer, and a child ask-bot span.
  • Each trace has a valid boolean correctness score. Failures are recorded with error status, not as empty successful answers.
  • Keys are read from .env and are not committed (.env is in .gitignore).
  • eval/NOTES.md contains a trace observation and no secrets.
Hints
  • A short-lived process may exit before sending events unless you call flushAsync().
  • A score is linked through traceId using Langfuse's public scores API.
  • Optional: save usage if DIAL returns it. If usage is missing, do not substitute zeros or estimates based on text length.
  • If the bot has multiple steps (retrieval → LLM), create a span for each. In Module 5, you will add a retrieve span to this structure.
  • A possible sign of an agent loop is an unusually large number of nested spans and a long duration, despite a low error rate.

Module final task

KnowledgeBot evaluation pipeline

Required: 4.1–4.4; 4.5 is optional Time: ~1 hour Deliverables: code + eval/report.json + eval/NOTES.md
Scenario: the team is preparing a new KnowledgeBot version for review. The command npm run eval -- --limit=2 runs two cases, calculates metrics, calls the pointwise judge, saves a report, and sends traces to Langfuse. Baseline comparison is disabled for this run.

Requirements

  1. Traced execution. Run each selected case through tracedAsk() (4.4); save usage only if DIAL returns it.
  2. Metrics and threshold. score() (4.2) returns correctness, sourceCoverage, and refusalAccuracy. Fail the run if correctness or sourceCoverage is below 0.75.
  3. Judge. Call judge() for every case. Only valid judgeScore values of 1–5 are recorded as Langfuse scores. Exclude parse errors from the average and disagreements, record them as errors in the report, and fail the run.
  4. Report. Save eval/report.json with metrics, average judge score, p95 latency, request error rate, and token-usage coverage.
  5. Operational note. In eval/NOTES.md, record one trace observation, a threshold for one metric, and the person responsible for responding.

Steps

  1. Run npm run eval:offline and check the local report without network calls.
  2. Configure DIAL and Langfuse, then run npm run eval -- --limit=2.
  3. Inspect the two traces and report; record your conclusions in eval/NOTES.md.
  4. Optional: run npm run eval:compare to compare against the baseline.
